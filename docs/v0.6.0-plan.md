# v0.6.0 — Focusing Release

## Vision

**Organon does one thing excellently: encode constraints and bind them to code and tests.**

Everything else — how you manage change (RFCs, ADRs, issues), how you improve your methodology over time (compounding, observations), how you orchestrate agents (skills, workflows) — is a *process layer* that sits on top. Different teams do it differently. Organon should not prescribe it.

v0.6.0 removes the process layer from Organon's scope. The result is a smaller, sharper tool with a clearer value proposition and less maintenance burden.

---

## What Organon Owns (Post-0.6.0)

### 1. The Organon Files

The specification of what a valid organon looks like:
- **ETHOS.md** — constraints, invariants, principles, decision heuristics
- **PHILOSOPHY.md** — reasoning behind the constraints
- **PROTOCOL.md** — step-by-step procedures
- **Frontmatter system** — YAML metadata enabling progressive disclosure
- **Scope hierarchy** — product → domain → feature → component inheritance

### 2. Bidirectional Bindings

The connection between organon constraints and the codebase:
- **Invariant stable IDs** (INV-SCOPE-N format) that survive refactoring
- **`@organon-invariant` annotations** in test files linking tests to invariants
- **Invariant coverage gate** — every invariant must have ≥1 tier-4 test
- **Reference integrity** — every `inherits_from`, `loads`, `protocol_file` path resolves

### 3. Structural Verification

Automated checks that the organon is correct, complete, and bound:
- Frontmatter valid and accurate
- References resolve
- Bindings are bidirectional (no orphans)
- Invariant coverage satisfied
- No stale files

## What Leaves Scope

### RFC Process
Change management is not Organon's business. Teams use GitHub issues, ADRs, Jira, Linear, PRDs — whatever fits their workflow. Organon will no longer document an RFC lifecycle, provide RFC templates, or maintain RFC-specific frontmatter fields.

*Organon will continue using RFCs internally for its own evolution, but will not prescribe them to users.*

### Compounding
The COMPOUND phase (reserving session time for methodology improvement) is a valuable practice, but it belongs to a *meta-methodology layer* that users compose on top of Organon. It is not Organon's core responsibility.

### Workflow & Skill Authoring
Organon will no longer specify how to write Claude skills, Cursor rules, or agent runbooks. The *binding contract* (protocol declares → code implements → test verifies) is Organon's business. The *agent orchestration format* is not.

### Observations System
The observations lifecycle (signal → pattern → actionable → resolved) supports compounding. With compounding out of scope, the observations system is optional and will no longer be part of the core methodology spec.

## The Simplified Enforcement Loop

**Before:**
```
DEFINE → BIND → EXECUTE → VERIFY → COMPOUND → EVOLVE
```

**After:**
```
DEFINE → BIND → EXECUTE → VERIFY
```

- **DEFINE** — Write organon files (ETHOS, PHILOSOPHY, PROTOCOL) encoding your constraints
- **BIND** — Annotate code and tests with invariant IDs (`@organon-invariant INV-X-N`)
- **EXECUTE** — LLMs read organon files and work within the encoded constraints
- **VERIFY** — `organon verify` checks that bindings hold and constraints are met

Evolving the organon (updating constraints as the project changes) is implicit in DEFINE — you rewrite your organon files when the project changes. How you decide to change them is up to you.

## What Does NOT Change

- The organon file spec (ETHOS/PHILOSOPHY/PROTOCOL structure)
- Frontmatter system (core fields)
- Scope hierarchy and inheritance rules
- Invariant stable IDs and `@organon-invariant` annotation contract
- The testing framework (packages/testing/) — `testInvariant` is core
- Progressive disclosure model
- `organon verify` and `organon health`
- book-humans/ (unaffected — philosophical narrative continues)

- A new user can understand the full methodology in 30 minutes (no RFC lifecycle to learn)
- `book-llms/` has no RFC or compounding content
- `organon verify` passes with 0 pre-existing failures (pay down technical debt as part of this release)
- The README's enforcement loop shows 4 phases, not 6
